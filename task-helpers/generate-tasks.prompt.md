# Rule: Generating a Task List from a PRD

## Goal

To guide an AI assistant in creating a detailed, step-by-step task list in Markdown format based on an existing Product Requirements Document (PRD).
By default, the task list should use a conventional implementation sequence rather than requiring Test-Driven Development (TDD).
When a user is available to answer questions, offer them the choice between a conventional task list and a TDD-oriented task list before generating tasks.

## Output

- **Format:** Markdown (`.md`)
- **Location:** The same directory as the source PRD
- **Filename:** `tasks-[prd-file-name].md` (e.g., `tasks-prd-user-profile-editing.md`)

## Multi-Model Execution (Best-of-Both)

When more than one model is available in the host environment, this prompt **must** be executed by two models in parallel and the outputs merged into a single final task list. This produces higher-quality task decomposition by combining the strengths of each model.

### Default Models

- **Model A:** `claude-opus-4-7` (Opus)
- **Model B:** `gpt-5.4`

If either default model is unavailable, fall back to the next most capable available model from the same family. If only one model is available, execute the prompt with that single model and skip the merge step (note this in the output header).

### Orchestration Flow

1. **Prepare:** Complete Steps 1–3 of the Process to identify the PRD, choose the task methodology, and analyze the requirements.
2. **Fan-out — Phase 1 (Parent Tasks):** Dispatch the PRD and selected methodology to both models simultaneously.
   Each model independently performs Step 4 of the Process and returns its parent-task list.
3. **Merge — Phase 1:** A merge step, performed by Model A acting as orchestrator, compares both parent-task lists and produces a single merged parent-task list using the **Merge Criteria** below.
   Present the merged list to the user and wait for "Go" as described in Step 5 of the Process.
4. **Fan-out — Phase 2 (Sub-Tasks):** After confirmation, or immediately when no user is available, dispatch the merged parent-task list and selected methodology to both models simultaneously.
   Each model independently performs Steps 6–8 to generate sub-tasks, relevant files, and verification criteria.
5. **Merge — Phase 2:** The orchestrator merges sub-tasks, relevant files, and verification criteria using the **Merge Criteria** below into the final document in Step 9, then saves it in Step 10.

### Merge Criteria ("Best of Both")

When merging two candidate outputs, prefer the version (or combine elements) that better satisfies, in priority order:

1. **PRD coverage** — captures every functional requirement, user story, and acceptance criterion from the PRD; no gaps.
2. **Selected methodology adherence** — follows the user's selected conventional or TDD workflow consistently.
   For TDD task lists, strictly order test-writing sub-tasks before the "run tests to confirm they fail" step and before implementation sub-tasks for every parent task that involves code.
   For conventional task lists, order implementation sub-tasks logically and include testing after or alongside implementation where appropriate.
3. **Specificity** — tasks name concrete files, functions, behaviors, or scenarios rather than vague verbs ("implement logic").
4. **Logical sequencing** — earlier tasks unblock later ones; dependencies flow forward.
5. **Junior-developer clarity** — a junior developer could pick up any single sub-task and act on it without re-deriving context.
6. **Conciseness** — when two candidates are equally clear, prefer the more concise phrasing; do not duplicate the same task expressed two ways.

When the two outputs disagree on structure (e.g., different parent-task groupings), choose the grouping that better reflects natural seams in the PRD and absorb non-overlapping useful sub-tasks from the rejected grouping into the chosen one. Deduplicate aggressively — a merged list with redundant tasks is worse than either input alone.

### Output Header

Prepend the merged task list with a brief HTML comment recording the models used, e.g.:

```markdown
<!-- Generated by multi-model merge: Model A = claude-opus-4-7, Model B = gpt-5.4 -->
```

If only one model ran, record that instead (e.g., `<!-- Generated by single model: claude-opus-4-7 (gpt-5.4 unavailable) -->`).

## Process

1.  **Receive PRD Reference:** The user points the AI to a specific PRD file
2.  **Choose Task Methodology:** If a user is available to respond, ask whether they want a conventional task list or a TDD-oriented task list.
    Present conventional tasks as the default choice.
    If no user is available to respond, proceed with the conventional approach.
3.  **Analyze PRD:** The AI reads and analyzes the functional requirements, user stories, and other sections of the specified PRD.
4.  **Phase 1: Generate Parent Tasks:** Based on the PRD analysis and selected methodology, create the file and generate the main, high-level tasks required to implement the feature.
    Use your judgement on how many high-level tasks to use.
    It is likely to be about 5.
    Present these tasks to the user in the specified format without sub-tasks.
    Inform the user: "I have generated the high-level tasks based on the PRD. Ready to generate the sub-tasks? Respond with 'Go' to proceed."
5.  **Wait for Confirmation:** Pause and wait for the user to respond with "Go".
    If no user is available to respond, continue automatically.
6.  **Phase 2: Generate Sub-Tasks:** Break down each parent task into smaller, actionable sub-tasks necessary to complete the parent task.
    For a conventional task list, order implementation tasks logically and add appropriate testing, validation, and cleanup tasks without requiring tests to be written first.
    For a TDD-oriented task list, generate the test-writing sub-tasks first, then a dedicated "run tests to confirm they fail" sub-task, then the implementation sub-tasks.
    TDD test sub-tasks should define the expected behavior, inputs, outputs, and edge cases derived from the PRD before any implementation code is written.
    Ensure sub-tasks logically follow from the parent task and cover the implementation details implied by the PRD.
7.  **Identify Relevant Files:** Based on the tasks and PRD, identify potential files that will need to be created or modified.
    List these under the `Relevant Files` section, including corresponding test files if applicable.
8.  **Generate Verification Criteria:** Based on the PRD's acceptance criteria and the tasks generated, write a `## Verification Criteria` section at the bottom of the document.
    Each criterion should be a concrete, observable check, such as a command to run, a scenario to test, or a behavior to confirm, that proves the feature works as specified.
    Use checkboxes (`- [ ]`) so they can be marked off during review.
9.  **Generate Final Output:** Combine the parent tasks, sub-tasks, relevant files, notes, and verification criteria into the final Markdown structure.
10. **Save Task List:** Save the generated document in the same directory as the source PRD with the filename `tasks-[prd-file-name].md`, where `[prd-file-name]` matches the base name of the input PRD file.
    For example, if the input is `tasks/user-profile-editing/prd-user-profile-editing.md`, save the output as `tasks/user-profile-editing/tasks-prd-user-profile-editing.md`.

## Output Format

The generated task list _must_ follow this structure:

```markdown
## Relevant Files

- `path/to/potential/file1.ts` - Brief description of why this file is relevant (e.g., Contains the main component for this feature).
- `path/to/file1.test.ts` - Unit tests for `file1.ts`.
- `path/to/another/file.tsx` - Brief description (e.g., API route handler for data submission).
- `path/to/another/file.test.tsx` - Unit tests for `another/file.tsx`.
- `lib/utils/helpers.ts` - Brief description (e.g., Utility functions needed for calculations).
- `lib/utils/helpers.test.ts` - Unit tests for `helpers.ts`.

### Notes

- **Task methodology:** [Conventional or Test-Driven Development (TDD), matching the selected methodology.]
- [For a conventional task list: Implement each feature in logical dependency order and include appropriate automated tests and validation.]
- [For a TDD-oriented task list: Write tests first, verify they fail, and then write the implementation to make them pass.]
- Unit tests should typically be placed alongside the code files they are testing (e.g., `MyComponent.tsx` and `MyComponent.test.tsx` in the same directory).
- Use the project's existing test commands and conventions.

## Tasks

- [ ] 1.0 Parent Task Title
  - [ ] 1.1 Implement [first logical part of feature/component]
  - [ ] 1.2 Implement [next logical part of feature/component]
  - [ ] 1.3 Add or update tests for [feature/component]
  - [ ] 1.4 Run relevant tests and validation
- [ ] 2.0 Parent Task Title
  - [ ] 2.1 Implement [first logical part]
  - [ ] 2.2 Add or update tests
  - [ ] 2.3 Run relevant tests and validation
- [ ] 3.0 Parent Task Title (may not require sub-tasks if purely structural or configuration)

## Verification Criteria

How we know the tasks have been successfully implemented:

- [ ] [Concrete, observable check derived from the PRD — e.g., "Run a specific scenario end-to-end and confirm expected output"]
- [ ] [Test suite command and expected result — e.g., "Run `uv run pytest path/to/tests/` and confirm all tests pass"]
- [ ] [Any additional acceptance criteria from the PRD that can be manually or automatically verified]
```

## Interaction Model

When a user is available, first ask them to choose between the default conventional methodology and a TDD-oriented methodology.
The process then pauses after generating parent tasks to get user confirmation ("Go") before proceeding to detailed sub-tasks.
These interactions ensure the methodology and high-level plan align with user expectations.
When no user is available to respond, use the conventional methodology and continue without pausing.

## Task Methodologies

### Conventional Workflow (Default)

Order sub-tasks according to implementation dependencies.
Include automated tests, manual validation, and refactoring where appropriate, but do not require every test to be written before its corresponding implementation.

### Test-Driven Development Workflow

When the user selects TDD, each parent task should follow the **Red-Green-Refactor** cycle:

1. **Red:** Write tests that define the expected behavior based on the PRD and run them to confirm they fail.
2. **Green:** Write the minimum implementation code to make the tests pass.
3. **Refactor:** Clean up the implementation while ensuring all tests remain green.

For TDD task lists, all test-writing sub-tasks must come before implementation sub-tasks.
Every parent task that includes tests must have an explicit "Run tests to confirm they fail" sub-task between writing tests and writing implementation.
Never skip this step or combine it with the test-writing step.

## Target Audience

Assume the primary reader of the task list is a **junior developer** who will implement the feature.
